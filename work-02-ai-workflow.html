팀원마다 달랐던 AI 코딩 도구 사용을 직접 제안해 표준화하고, Claude Code 플러그인으로 배포·운영했습니다. 개발자 8명 중 6명이 실사용하고 나머지 2명은 설치를 진행 중이며, 활성 프로젝트 11개에 정착시켰습니다.

기간 2026.1Q 운영 시작 → 06 플러그인화 → 현재 역할 제안·기획·설계·구현·배포·온보딩 전 과정 오너 (TF 리드: 본인 + 프론트엔드 2명) 릴리스 v1.3.0 정식(2026.08.05) → v1.4.0(08.12)

1 문제

팀원들이 Claude·Codex를 개인적으로 알아서 쓰면서 두 가지 편차가 생겼습니다. 하나는 산출물 품질의 개인 편차로, 같은 도구를 쓰는데도 결과 수준이 크게 갈렸습니다. 다른 하나는 기록·리뷰 절차의 편차로, 계획·진행·리뷰 기록의 형식과 유무가 극단적으로 갈렸습니다. 지시받은 과제가 아니라 본인이 문제를 정의해 제안했고, 팀 내 AI 도구 활용 경험을 바탕으로 전체 개발자의 생산성을 높이는 TF 리드를 맡았습니다.

목표를 "AI를 잘 쓰게 하자"가 아니라 "기록을 잘 남기는 문화로 가자"로 정한 것이 이 프로젝트의 방향을 결정했고, 뒤의 측정 플랫폼(UX AI Hub)이 자연스럽게 이어진 이유이기도 합니다.

2 맡은 역할

제안부터 기획·설계·구현·배포·팀 온보딩까지 전 과정의 오너였습니다. 구현보다 어려웠던 것은 "무엇을 만들어야 팀에 실제로 도움이 되는가"를 정하는 일이었고, 만들기 전에 팀 기존 워크플로를 조사하고 PoC로 먼저 검증했으며 AI 트렌드를 지속 추적했습니다.

3 핵심 판단과 설계

작업 시작부터 MR까지, 하나의 흐름

/start → 개발 → /note → /commit → /review → /mr

개별 명령이 아니라 흐름 전체를 스킬 12종으로 정의했습니다. 가장 공을 들인 것은 /start입니다. 1Q 피드백에서 "구현 이후 수정보다 계획 단계에서 방향을 맞추는 것이 더 효과적"임이 확인됐기 때문에, 목적과 범위, 접근, 참고 자료를 먼저 정리한 뒤 Jira·GitLab Issue·Branch·progress.md를 연결합니다. 손으로 .claude를 복사하던 배포는 플러그인 마켓플레이스 + /team-init 두 단계로 바꿨고, 프론트엔드 전용 규칙을 Android·iOS·NestJS 멀티스택으로 확장하고 ISMS-P 보안 규칙을 연결했습니다.

"리뷰가 무겁다"는 클레임: 기준 완화가 아니라 라우팅

배포 후 "혹시 리뷰가 원래 이렇게 느린가요?"라는 클레임이 왔습니다. 같은 리뷰 루프에 5주 전에는 "리뷰 루프 좀 많이 좋은 것 같습니다"라는 정반대 반응이 있었기에, 품질 문제가 아니라 작업 범위에 따라 적정 강도가 다른 문제로 진단했습니다. 위험도별 5단계 프리셋(Trivial~Deep) 자동 라우팅을 하루 만에 배포하되, 상용·인증·개인정보·결제는 강제 Deep으로 하향을 차단하고 어떤 프리셋에서도 팀 공통 Baseline 9항은 생략되지 않게 했습니다.

"조용히 실패하는 것"을 문제로 정의

고친 결함의 상당수는 에러를 내지 않아 아무도 신고하지 않던 것이었습니다. 포맷 훅이 Windows에서 배포 이래 아무 메시지도 없이 실패하던 문제, 훅 4종이 아예 배포되지 않던 문제, 타입체크가 검사 대상 0개로 항상 성공하던 문제가 여기에 해당합니다. 재발 방지를 문장이 아니라 실행되는 기계 검증(하네스 301건, validate-skills)으로 바꿨습니다.

사람이 잊는 절차를 도구가 확인하게: 가드레일 훅 8종

가드레일 훅은 타입 에러 커밋 차단, CHANGELOG 누락 경고, 민감 파일 편집 알림, E2E 안티패턴 경고, 자동 포맷, 사용·차단 이벤트 수집을 담당합니다. 가드레일 훅은 커밋 차단의 임계 경로에 있어, 기록(동기)과 전송(비동기)을 분리해 가드레일이 스스로 깨지지 않게 설계했습니다.

표준화의 유지비용까지 자동화

도구를 표준화하면 그 도구의 업데이트가 팀 전체의 리스크가 됩니다. 매일 오전 Claude Code 릴리즈 노트를 확인해 영향도 기준으로 분류하고 팀 Slack에 노티하는 릴리즈 모니터링 봇을 함께 운영 중입니다.

4 해결 과정: 만든 것보다 정착시킨 것

시기단계

2026 2Q1Q 운영 피드백 수집 → 체계 재설계 → 팀 세션 PT 직접 진행

2026.07 – 08가드레일·리뷰 라우팅·게이트 고도화 → v1.3.0 정식 → v1.4.0

각자 편한 방식으로 쓰던 사람들에게 표준을 요구하는 상황이라 "납득이 먼저"라고 판단했습니다. 팀 세션 발표는 결론에 해당하는 도구를 먼저 제시하지 않고 ①1Q 피드백 근거 → ②왜 필요한가 → ③무엇을 자동화하는가 → ④어떻게 쓰는가 순서로 구성했고, 완성품을 통보하는 자리가 아니라 설계 과정을 공유해 의견을 받는 자리로 만들었습니다.

릴리스 공지에는 적용 방법·변경 사항·확인 사항과 함께 기존 설치자가 겪을 충돌까지 미리 안내했습니다. 만들어서 배포하는 데 그치지 않고 마이그레이션 비용까지 설계했습니다.

7 배운 점과 다음

리뷰 클레임에서 배운 것은 "내 효율 기준을 팀의 기준이라고 가정했다"는 점입니다. 20분짜리 리뷰가 나에게는 감당 가능한 비용이었지만 모든 작업 범위에 맞는 기준은 아니었고, 해법은 기준을 낮추는 것이 아니라 위험도에 따라 조절 가능하게 만드는 것이었습니다.

이 표준화는 더 큰 계획의 1단계입니다. 표준화(도구)에서 측정(UX AI Hub)으로 이어지는 팀 AI 인프라 로드맵을 실행하고 있습니다. 다음 단계인 지식 축적은 후속 과제로 LLM wiki와 RAG 기반 팀 위키를 설계하고 있습니다.
