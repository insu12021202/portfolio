표준화한 워크플로의 사용 현황과 효과를 검증하고, 개선 근거를 확보하기 위해 구축했습니다. 지표 정의부터 NestJS·PostgreSQL 수집 서버, AWS 배포, 대시보드 프론트엔드까지 전 영역을 단독으로 구현했습니다. 본부 단위 보고와 플러그인 개선을 위한 의사결정 근거로 쓰도록 설계했습니다.

기간 2026.07 – 현재 (MVP 완료, 고도화 중) 역할 TF 리드 · 서버·지표·인프라·프론트엔드 전 영역 단독 구현 스택 NestJS · PostgreSQL · AWS(TLS·systemd) · Vue 3

1 문제

만든 도구를 계속 개선하려면 쓰이는 방식을 알아야 했습니다. 어떤 스킬이 실제로 쓰이는지, 문서 연결률과 리뷰 리드타임은 어떤지를 확인해야 했습니다. 동시에 표준화의 효과를 본부 단위 보고에 숫자로 제시할 수 있어야 했습니다. 제품 개선의 근거가 실제 동기였고, 성과 보고는 그 부산물입니다.

2 맡은 역할

TF 리드로서 지표 정의부터 수집·집계 서버, AWS 배포, 대시보드 프론트엔드까지 전 영역을 단독 구현했습니다. 프론트엔드와 백엔드를 혼자 만들면서도 API 계약서를 SSOT로 두고 먼저 갱신한 뒤 구현하는 규율을 유지했고, 그 덕에 구현 착수 전에 API 계약의 불일치를 발견해 고친 적도 있습니다.

3 핵심 판단과 설계

지표를 목적에서 역산했다

측정 가능한 항목부터 나열하지 않고, 관리자가 알고 싶은 것(5가지 질문 축) → 그것을 답해 줄 지표 → 실제 수집 가능성의 순서로 설계했습니다. Reach, 가드레일 성과, 절차 퍼널, 효과, 준수율이 그 결과입니다.

일부러 재지 않기로 한 것

세션에서 오간 개개인의 대화 내용은 수집하지 않습니다. 민감 파일 경고도 패턴 종류(env·token)만 남기고 경로는 남기지 않습니다. 경로를 넣으면 이 훅이 지키려는 대상의 위치가 수집 데이터에 쌓이는 자기모순이 되기 때문입니다.

평가 도구로 오용되지 않게

관리자 전용 토큰을 분리하고(교차 사용 양방향 401) 사람 단위 지표를 권한으로 잠갔으며, 퍼널의 담당자 이름은 서버에서 권한별로 분기했습니다. 화면에서 가리더라도 개발자도구로는 보이는 문제를 서버에서 해결했습니다. 팀원 화면에는 "이 화면은 평가 자료가 아니에요. 표준이 자리잡도록 도울 사람을 찾는 데만 써요."라는 경고문을 직접 넣었습니다.

틀린 숫자보다 no_data

모든 지표에 신뢰도 배지를 붙이고, '집계 대기'(아직 안 셌음)와 '데이터 없음'(집계했는데 0건)을 다른 상태로 구분했습니다. 모집단이 어긋나 1350%로 계산되던 지표는 화면에서 제외했습니다. 숫자가 스스로 신뢰도를 말하게 하는 설계입니다.

4 해결 과정: 내 지표를 먼저 의심했다

수집 서버는 스킬·가드레일 이벤트 인제스트, git/GitLab 스캔 기반 재계산 파이프라인(매일 03:00 크론), 지수 백오프 재시도, 부분 실패 시 우아한 강등, recompute 실행 이력을 갖춥니다. AWS 배포(TLS·systemd·인증서 자동 갱신)는 인프라팀 가이드를 받아 직접 수행했습니다. 진짜 난도는 기술이 아니라 지표가 거짓말하지 않게 만드는 것이었습니다. 체감과 다른 숫자를 발견할 때마다 추적해 교정했습니다:

왜곡원인과 조치
준수율 4% 붕괴미도입 레포 1,233커밋이 분모에 유입 → 로스터 + 도입일 2단계 게이트
커밋 130건 통째 누락도입일이 미래로 밀리는 부트스트랩 역설 → 후보 최소값 채택 + 단조 감소만 허용
평균 리드타임 14.2h소수 이상치가 지배 (중앙값 2.7h) → 업무시간 기준 중앙값·임계값 내 비율로 재정의
채택률 1350% → 100% 클램프분자·분모의 모집단 불일치 → 화면에서 제외, 결과 지표(문서 위생)로 대체

7 배운 점과 다음

이 프로젝트의 실제 난도는 서버 구축이 아니라 지표가 거짓말하지 않게 만드는 것이었습니다. "체감과 다른데?"라는 감각을 무시하지 않고 추적하면 왜곡은 하나씩 교정할 수 있었고, 그 과정에서 "왜곡된 숫자보다 no_data가 낫다"가 판단 기준이 됐습니다.
