팀에 배포한 AI 개발 플러그인이 실제 업무에서 어떻게 사용되는지 확인하고, 개선 방향을 판단하기 위해 구축한 플랫폼입니다. 스킬 사용 현황, 프로젝트별 개발 활동, 작업 문서와 리뷰 기록을 살펴볼 수 있도록 지표 설계부터 수집·집계 서버, AWS 배포, 대시보드까지 직접 구현했습니다.

기간 2026.07 – 현재 (MVP 완료, 고도화 중) 역할 TF 리드 · 지표 설계·수집 서버·인프라·대시보드 단독 구현 스택 NestJS · PostgreSQL · AWS · Vue 3

1 배경과 목표

플러그인을 배포한 뒤에도 실제 업무에서 의도한 대로 사용되는지 확인할 필요가 있었습니다. 어떤 스킬이 사용되는지, 프로젝트별 개발 활동이 어떻게 변하는지, 작업 계획·진행 문서와 리뷰 기록이 남고 연결되는지를 살펴보고자 했습니다.

사용 현황을 한곳에서 확인하고, 예상과 다른 사용 흐름이 발견되면 원인을 조사해 플러그인의 개선 방향을 정할 수 있는 환경을 만드는 것이 목표였습니다.

2 맡은 역할

확인하려는 질문을 지표로 구체화하고, NestJS·PostgreSQL 기반 수집·집계 서버와 대시보드 프론트엔드를 단독 구현했습니다. 스킬·가드레일 이벤트와 git·GitLab 작업 기록을 수집하고, 이를 집계해 화면에 제공하는 흐름을 구성했습니다.

API 계약을 기준으로 서버와 화면을 연결했으며, 인프라팀 가이드를 바탕으로 AWS 배포와 운영 설정을 직접 수행했습니다.

3 측정과 데이터 설계

확인하려는 질문에서 지표 정의

기능의 사용 횟수만 모으는 데 그치지 않고, 플러그인이 실제 작업 과정에 어떻게 사용되는지 확인할 수 있도록 지표를 구성했습니다.

수집 범위와 접근 권한 구분

세션에서 오간 개인별 대화 내용은 수집하지 않도록 범위를 정했습니다. 민감 파일 경고는 파일 경로 대신 env·token 등의 패턴 종류를 기록하도록 구성했습니다.

개인별 지표는 권한에 따라 접근할 수 있도록 분리하고, 서버에서 응답 범위를 구분했습니다. 화면 표시뿐 아니라 데이터 제공 단계에서도 접근 조건을 적용했습니다.

산출 상태와 근거 표시

지표의 산출 방식과 신뢰도 정보를 함께 표시해, 숫자를 해석할 때 필요한 조건을 확인할 수 있도록 했습니다. 집계 상태와 산출 근거를 화면에서 안내하고, 집계 대상이나 계산 기준이 맞지 않는 지표는 그대로 노출하지 않도록 정비했습니다.

4 발견과 개선

대표 사례: 실제 작업에 맞춘 리뷰 방식 조정

  1. 관측
    데이터에서 리뷰 기록 없이 머지되는 사례를 발견했습니다.
  2. 원인 확인
    작은 작업이나 일정상 빠르게 머지해 확인해야 하는 상황이 있음을 확인했습니다.
  3. 개선
    review 스킬이 작업 범위를 파악하고, 간단 리뷰 또는 기존의 독립 에이전트 반복 리뷰를 선택할 수 있도록 개선했습니다. 반복 리뷰는 머지 전 필수 수정 사항인 blocker가 없는 상태가 될 때까지 진행합니다.

집계 조건 검증

사용 현황을 해석하기 전에 집계 대상과 기간, 계산 방식도 확인했습니다. 도입하지 않은 프로젝트가 포함되거나 일부 기록이 누락되는 경우를 보정하고, 평균값만으로 실제 작업 흐름을 판단하지 않도록 지표를 조정했습니다.

확인한 문제조치
미도입 저장소의 기록이 집계에 포함됨도입 대상과 도입일을 기준으로 집계 범위 정비
도입 시점 산정으로 일부 작업 기록이 누락됨도입 시점 산정 로직 보정
일부 긴 작업이 평균 리드타임에 크게 영향을 줌업무시간 기준 중앙값과 기준 시간 내 비율로 지표 보완

7 배운 점

데이터에서 예상과 다른 사용 흐름을 발견한 뒤, 실제 업무 상황을 확인해야 개선 방향을 정할 수 있었습니다. 리뷰 기록이 없는 사례도 작업 범위와 일정이라는 맥락을 확인한 뒤 리뷰 방식 개선으로 연결했습니다. 측정 대상과 계산 기준을 검증하는 일과, 사용자의 업무를 이해하는 일이 함께 이루어져야 데이터가 도구 개선의 근거가 된다는 점을 배웠습니다.
