착수 당시 본부 주력 과제였고, 현재 전사가 쓰는 메인 사내 LLM 챗봇입니다. 전사 약 200명을 대상으로 배포되어 약 100명이 실사용하며, 월 2.56억 토큰을 처리합니다. 프론트엔드를 0부터 1년간 단독으로 맡아 채팅에서 아티팩트 협업까지 확장했습니다.

기간 2025.07 – 2026.07 (약 1년) 역할 프론트엔드 단독 개발 (개발·리뷰·검수 전 과정) MR 103건 작성 / 101건 머지 (전 프로젝트 중 최다) 스택 Vue 3 · TypeScript · SSE · TipTap

1 문제

문제는 "채팅 UI를 만드는 것"이 아니었습니다. LLM은 규격대로 답하지 않고(출력이 계약이 아니라 확률), 브라우저에는 Canvas 최대 크기 같은 숨은 제약이 있으며, 전사 서비스에는 보안 감사 수준의 요건이 추가로 요구됩니다. 이런 조건에서 전사 서비스가 요구하는 운영 품질을 1년간 유지하는 것이 핵심 과제였습니다.

2 맡은 역할

초기 구축(0→1)부터 협업 기능까지 프론트엔드 전체를 단독으로 담당했습니다. 구체적인 범위는 멀티 LLM 채팅, SSO 인증/인가, 세션 관리, 파일 입력·미리보기(이미지·PDF·Office·PPT), 대화 폴더링·즐겨찾기·아카이브, 사고 과정 노출, 그리고 아티팩트의 생성·편집·버전 관리·Diff·공유·권한·편집 잠금·임시저장입니다.

3 핵심 판단과 설계

동시 편집 대신 편집 잠금

사내 문서 협업 규모에서 CRDT/OT의 복잡도와 서버 비용을 감당할 이유가 없다고 판단해 편집 잠금을 택했습니다. 대신 잠금 방식의 알려진 약점(잠근 채 자리를 비우는 사람)을 heartbeat polling + 비활성 자동 해제로 선제 차단했습니다.

형식의 한계를 인정하는 경로

GFM 테이블은 셀 내부 블록 요소를 지원하지 않아 복잡한 테이블 콘텐츠가 소실됐습니다. "전부 마크다운으로 변환한다"는 원칙을 고수하는 대신, 복잡한 테이블은 변환하지 않고 HTML로 유지하는 경로를 신설해 콘텐츠 소실을 막았습니다.

감사가 오기 전에 막는 보안

외부 보안 감사가 예정된 상황에서 지적을 기다리지 않고 선제 조치했습니다. 공유 링크 로그인을 필수화하고, Open Redirect를 방어했으며(단위 테스트 22건), window.open을 통한 인증 우회를 차단하고, accessToken을 HttpOnly 쿠키로 전환했으며, 외부 IP에는 MFA를 적용했습니다. 전환에 따라온 Token Rotation의 refresh 중복 호출은 Promise 병합 패턴으로 일원화했습니다.

배포 경험에서 출발한 성능 개선

개발 서버 배포를 직접 하다가 번들이 무겁다고 느껴 착수했습니다. 라우터 비동기 로드 + 아티팩트 컴포넌트 분리 + 벤더 청크 분리(vue·tiptap·office·markdown·pdf·utils)로 메인 번들을 2,376KB에서 455KB로 줄였고, 앱 코드만 바뀌면 벤더 청크 캐시가 유지되어 재방문 로딩에도 이득이 있습니다.

"모델이 규격대로 답하지 않는다"는 문제에 대응한 기록

LLM 프로덕트의 프론트엔드에만 존재하는 문제군을 하나씩 정의하고 해결했습니다. 예를 들면 LLM이 •·→ 같은 비표준 불릿으로 답하는 문제(9종을 변환하되 들여쓰기·코드블록 보존), 자체 전처리 정규식이 오히려 볼드를 깨던 문제(marked가 이미 정상 처리하고 있었으므로 전처리를 제거), LaTeX를 지원하지 않는 문제(유니코드로 치환), 그리고 앞에서 설명한 GFM 테이블의 한계가 있었습니다.

대용량 PDF: 브라우저 제약 수준까지 확인한 원인 규명

47페이지 이상 아티팩트가 빈 PDF로 나오던 문제의 원인은 브라우저별 Canvas 최대 높이 제한(Chrome 약 16,384px / Safari 약 4,096px)이었습니다. 47페이지는 약 105,562px에 해당하기 때문에 렌더링 자체가 실패하고 있었습니다. 그래서 html2pdf.js를 제거하고 파이프라인을 직접 구성했습니다.

마크다운 → HTML → iframe 렌더링 → 코드블록 이미지화 → 청크 캡처(8,000px) → CPU 크롭 → PDF

청크 높이는 모든 브라우저가 호환되는 8,000px로 고정하고, 페이지 높이의 정수 배로 설정해 페이지 경계에서 섹션이 소실되지 않게 했습니다.

7 배운 점과 다음

LLM 프로덕트 프론트엔드의 핵심은 "출력이 계약이 아니라 확률"이라는 전제를 받아들이는 것이었습니다. 형식의 한계를 인정하고 변환하지 않는 경로를 만드는 일과, 라이브러리가 왜 실패하는지를 브라우저 제약 수준까지 확인해 규명하는 일은 모두 이 전제에서 나온 태도입니다.

남은 과제도 분명합니다. 번들 −81%가 실제 로딩 시간에 준 개선폭의 측정, 그리고 아티팩트 협업의 실사용률 확인은 아직 확보하지 못한 숫자입니다.
